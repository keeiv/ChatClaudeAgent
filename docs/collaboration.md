# 協作控制（0.8.0）

桌面版在右側「任務控制」開啟計畫、意見、關注點與隔離工作區；頻道設定也有入口。左側「收件匣」集中所有對話的待辦與完成通知。CLI 使用相同 C++ 核心。

## 計畫、核准與驗收

1. 開啟「計畫與驗收」，填標題、工作步驟、各步驟驗收條件，儲存草稿。可再增刪、編輯步驟。
2. 對整份計畫或單一步驟留言。每次儲存、留言都產生新版本；原有核准與驗收不再適用。留言保留版本標記。
3. 檢查目前版本後按「核准此版本」。這一步不啟動模型。
4. 另按「執行已核准計畫」，沿用目前對話的主刀、流程與權限。步驟、驗收標準及帶版本的留言一同交付，歷史留言不提高系統權限。
5. 模型結束後標為待驗收；失敗或中斷會保留狀態。人工核對證據後逐項勾選，全部勾選才是已驗收。重啟不會自動執行未完成計畫。

每份計畫最多 50 步、200 則留言，整份協作資料最多 2 MiB。工作中不能替換計畫；過期的版本操作會被拒絕。儲存失敗時保留原有決策。

CLI 範例：

```text
/plan import plan.json
/plan
/plan-comment 加入空字串與多位元組案例
/plan
/plan-approve
/plan-run
/plan
/plan-accept step-1
```

`plan.json`：

```json
{
  "title": "補齊輸入驗證",
  "steps": [
    { "text": "重現並修正空輸入", "acceptance": "空輸入與一般輸入的測試通過" }
  ]
}
```

核准是授權開始這份工作；驗收是對交付結果的人工確認，不代表程式另外執行了一次測試。

## 統一收件匣

列出所有對話的待核准、提問、暫停、中斷、計畫與完成通知，待處理事項優先，可開啟原對話及對應訊息。把對話標為已讀只隱藏一般通知，不略過模型核准、提問或計畫。最多顯示 300 項，超過時提示還有其他項目。CLI `/inbox` 列出對話識別與項目，可用 `/chat` 切換後處理。

提醒沿用既有的視窗閃爍／終端機提示；本版沒有新增 Windows 通知中心的點擊連結。

## 審查關注點

內建安全、效能、測試、相容性四份 Markdown 規則。桌面版可直接編輯或新增；一般互審及本地審查依成員指定，多代理流程依每個審查位置指定。作者位置不套用審查規則。流程引用的規則不存在時會阻擋啟動，要求重新選擇。

關注點補充檢查方向，不提高權限，也不免除專案規範、測試及取證要求。最多 24 份，每份 Markdown 最多 12000 bytes。

CLI `/focus` 檢查規則與指派；`/focus codex security` 指定 GPT；`/focus codex` 回復一般審查。`/focus-import focus.json` 替換完整清單：

```json
[
  { "id": "security", "name": "安全", "text": "檢查越權與敏感資訊；附重現條件及檔案行號。" },
  { "id": "transactions", "name": "資料一致性", "text": "檢查交易、重試、取消與重複寫入。" }
]
```

## 多模型獨立意見

選擇 2 至 4 位已就緒的 Claude、GPT 或兩位本地審查員，以同一問題平行獨立分析。每位有獨立工作階段，不取代原對話上下文；本地成員需先在設定啟用。Claude 使用規劃權限，GPT 使用唯讀沙箱，本地成員使用唯讀工具；此模式的升權請求會拒絕，要求補充資料時保留結果並提示修訂問題。

所有成員結束後，至少兩份有效意見才會另開一次整理回覆。保留每位原文，分開顯示共識、分歧及待驗證項目。整理者優先 GPT，否則使用成功回覆的第一位；這一輪也消耗所選模型的額度或本機資源。模型共識不等於事實，仍需核對證據。

按「將提案存成待核准計畫」只建立草稿；可編輯、留言、核准後另行執行。無效的結構化提案會保留原文，改為人工建立計畫，不自動猜測步驟。停止或重啟會保留已收結果，不默默重跑。

CLI：`/opinions claude,codex 問題`，`/opinions` 查看，`/opinions-stop` 停止，`/opinion-plan` 採用提案。此版成員為兩個訂閱後端及兩個本地位置；API 供應商仍供既有的多代理流程使用，尚未加入意見模式選單。

## Git worktree 隔離與合併

每個任務對話可從目前專案的已提交 HEAD 建立獨立 worktree 與主機產生的 `cca/…` 分支。來源必須有提交、位於分支且沒有未提交／未追蹤檔案；不自動暫存或複製未提交內容。之後該對話切到隔離路徑，清除舊代理 session，並保存來源、分支及目標資訊。

同一任務的順序代理在同一個 worktree 交接；不同任務用不同群組與 worktree，可互不覆蓋地工作。隔離對話綁定該路徑，其他專案另建對話。

合併流程：

1. 檢查並提交要合併的任務變更；目標也須乾淨，不能已有未完成的合併。
2. 按「檢查能否合併」，以 Git `merge-tree --write-tree` 預演。這一步不修改目標工作檔。
3. 確認目標、差異摘要和衝突狀態後，明確確認合併。主機再次比對兩側 HEAD 與預覽；過期或衝突時拒絕套用。
4. 成功時建立一般 Git 合併，保留任務分支和 worktree；失敗時保留可檢查資料，不強制解衝突。Git 的版本、使用者提交身分或 hooks 導致失敗時會顯示原因。

需要 Git 支援 `merge-tree --write-tree`；本機已用真實測試倉庫驗證。CCA 內部的檢查點仍是原有影子倉庫，不會被當作使用者 Git 的提交。CLI 依序使用 `/workspace create`、`/workspace check`、`/workspace merge`；最後一個指令本身就是明確合併操作。

worktree 放在 `%LOCALAPPDATA%\CCA\worktrees`，本版不自動刪除，以免遺失未合併工作；不再需要時可檢查後自行用 Git 清理。

## 保存與驗證範圍

協作決策以原子寫入保存到 `%APPDATA%\CCA\collaboration\<對話>.json`，關注點在 `settings.json`，對話、模型用量與任務紀錄沿用既有儲存。測試設定 `CCA_DATA_DIR`，worktree 也會轉到隔離測試目錄。

驗證分成真實 C++ 存檔／子程序協定／Git 與瀏覽器模擬互動。模擬模型沒有使用訂閱或付費 API，也不能代表真實模型品質；紀錄見 本次驗證。
