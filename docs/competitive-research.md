# 競品調查與改進方向（2026-10-25）

對象是使用者指定的六個產品。資料於 2026-10-25 查閱，來源列在文末。Aubia 尚未公開發行，Antigravity 2.0 的介面細節多半來自第三方評測，這兩項的描述可信度較低。

## 各產品值得參考的地方

| 產品 | 是什麼 | CCA 可以參考的做法 |
| --- | --- | --- |
| Microsoft Agent Framework | 建代理與多代理流程的開發框架（.NET、Python、Go），1.0 已發布 | 五種編排模式（依序、並行、交接、群聊、Magentic 管理者）；每種都支援串流、檢查點、暫停與續跑、人工核准。Magentic 模式先出計畫給人審，可退回重擬；卡住時可要求人工介入。DevUI 在本機瀏覽器即時畫出流程圖、訊息流與工具呼叫。 |
| OpenAI Codex（桌面版） | 多執行緒的寫程式桌面程式 | 審查窗格：範圍可切換未暫存、已暫存、單一提交、整個分支、上一輪；在某一行加留言再送回給代理；整份、單檔、單一區塊都能暫存或還原。`/review` 對分支或未提交變更做審查而不動工作區。另有 worktree 讓多個任務互不干擾、排程任務、Chat／Work 兩種模式。 |
| Google Antigravity 2.0 | 不含編輯器、專門管理代理的桌面程式（2026-05 發布） | 以「產物」為審查中心：計畫、任務清單、說明文件可以直接留言要求修改，或核准讓代理繼續。統一收件匣，代理完成或需要輸入時通知。專案可跨多個資料夾，各自有權限。`/goal`（做到完成為止）、`/grill-me`（動工前先追問需求）、`/schedule`。評測抱怨分不清是哪個代理、工作區切換送錯對象，這是 CCA 要避免的。 |
| Claude Code Agent Teams | Claude Code 的實驗功能，一位領隊加多位隊友 | 共用任務清單（待辦、進行中、完成，可設相依，完成後自動解鎖；用檔案鎖避免兩人搶同一項）。隊友之間直接傳訊，使用者可直接對任一隊友說話。`TaskCompleted`、`TeammateIdle` 鉤子可擋下不合格的完成。官方建議 3 到 5 位、每位 5 到 6 項工作，並要求分工到不同檔案以免互相覆蓋。 |
| Aubia | 讓不同模型家族互審的桌面駕駛艙（尚在 Beta） | 互審時間軸：每一輪標出代理、狀態與差異大小，並畫圖比較各輪改了多少行；預設 3 輪，持續的歧見交給使用者裁決。「意見→可執行計畫」：同一個技術問題問多個模型，整理出共識與分歧，產生可編輯、核准後執行的任務清單。每個代理有自己的 worktree 與分支，並顯示能否無衝突合併。 |
| Chorus（chorus.codes） | 多模型程式審查工具，用使用者既有的訂閱 | 審查者「人格」各有關注點：安全、跨平台、效能、成本、相依套件，各是一個可編輯的 Markdown 檔。作者與審查者來自不同模型家族。法定人數（例如全體同意）不足時，把分歧帶進下一輪。即時執行畫面顯示階段、耗時與成本上限。權限分三級：只讀、工作區、完全。 |

另一個同名專案 Chorus（chorus-ai.dev）是需求到交付的工作流程：需求釐清問答、PRD 與任務相依圖、看板（待辦、進行中、待驗證）、人工驗收每一條驗收標準。

## CCA 0.6.2 的位置

已經比上面多數產品走得遠的部分：

- 互審是 Claude 和 GPT 兩個不同家族，用使用者自己的訂閱，這正是 Aubia 與 Chorus 的賣點。
- 交接結果取自影子 Git 的實際差異，必要測試要有主機取得的結束碼，規範審查用程式檢查，而不是相信模型自述。
- 多代理流程最多 32 個位置、任務紀錄可續跑、API 供應商、MCP、Docker 沙箱、本地唯讀審查員。

相對落後或粗糙的部分（2026-10-25 實測，模擬資料）：

- 沒有審查窗格。檔案變更只能看 diff，不能在某一行留言送回、暫存或還原單一區塊。
- 沒有統一收件匣。待處理請求、暫停、完成散在各個對話裡。
- 群組標題列擠滿文字按鈕與瀏覽器原生下拉選單，視窗稍窄時模型名稱和資料夾被截成「GPT…」「sho.」。
- 閒置時流程圖仍佔聊天區約四分之一高度（1100×760 視窗）。
- 右側欄是一長串卡片（流程、最近協作、任務紀錄、本地審查員、來回上限、權限、額度）。
- 多代理流程設定是一長串表單，用「上移／下移」排序。代理清單是對話框裡的第二層捲動區（`.pipeline-editor`，最高 55vh），被切掉的下一位代理欄位緊貼「新增代理」按鈕，看起來像按鈕蓋住欄位。
- 只有兩方互審，沒有「先問多個模型再定計畫」，也沒有依關注點分工的審查者。
- 平行任務共用同一個工作資料夾，靠互斥鎖排隊，沒有 worktree 隔離。

## 建議順序

第一批：減少 Bug 與粗糙感（先做，不加新概念）

1. 修好目前所有測試失敗與上面的版面問題（流程設定的雙層捲動、標題列截斷、閒置流程圖）。
2. 標題列只留名稱與圖示按鈕；主刀、接手、模型、權限、資料夾收進一個「頻道設定」面板或彈出選單，不再用原生下拉選單。
3. 流程圖閒置時縮成一行狀態，工作中才展開。
4. 每個代理固定顏色與頭像，所有地方（訊息、流程、通知）一致，避免 Antigravity 評測提到的「分不清是哪個代理」。

第二批：審查體驗（最能拉開差距）

5. 審查窗格：依「這一輪／這個任務／未提交」切換範圍，逐檔、逐區塊還原；在某一行留言，下一輪自動帶給負責的代理（參考 Codex）。
6. 互審時間軸：每輪的代理、結論、差異行數與趨勢，歧見最後交給使用者裁決（參考 Aubia）。
7. 計畫與任務清單變成可留言、可核准的產物（參考 Antigravity）。

第三批：協作能力

8. 統一收件匣：所有對話需要你決定的事、完成通知集中一處，可從系統通知點進去。
9. 審查人格：除了角色語氣，再加「安全／效能／測試／相容性」等關注點，可指定給任一審查位置（參考 Chorus）。
10. 意見模式：同一個問題同時問 Claude、GPT 與本地模型，整理共識與分歧，產生可編輯的計畫再執行（參考 Aubia）。
11. 平行任務用 git worktree 隔離，完成時顯示能否無衝突合併（參考 Codex、Aubia）。

不建議跟進：語音輸入、排程任務、Magentic 式由模型動態指揮多代理。前兩項和寫程式協作的核心關係不大；第三項會讓流程難以預測，和 CCA 以主機證據為準的做法衝突。

## 0.7.0 已完成的部分（2026-10-25）

- 第一批：標題列改成一行摘要加圖示，設定收進頻道設定面板；閒置時流程圖只佔一行；側欄只留成員（依身分分組）、互審時間軸、任務紀錄與額度；多代理流程設定改成單層捲動，名稱、後端、角色同一列；新的視覺識別見 [visual-identity.md](visual-identity.md)。
- 第二批（部分）：審查窗格（範圍切換、逐檔與逐段還原、逐行意見）與互審時間軸。以下 0.8.0 再補上計畫與第三批功能。
- 介面補完：審查的檔案篩選、鍵盤切換、本機意見草稿、主機確認送出、還原前檢查新修改、過期回應防護及減少動態；登入與帳號外觀也套用作戰終端規則。

## 0.8.0 協作控制

本段描述本機實作，不重新驗證上方歷史競品資料，也不以模擬測試推論真實模型品質。

- **計畫產物**：編輯步驟與驗收條件、整份或指定步驟留言、版本比對、核准後另行執行；留言與編輯會取消原核准。完成工作進入待驗收，人工逐項確認。
- **統一收件匣**：跨對話列出核准、提問、暫停、中斷、待核准計畫及完成通知；可返回原對話。已讀不會略過必要核准。使用程式既有的視窗提醒；未增加 Windows 通知中心的深層連結。
- **審查關注點**：安全、效能、測試、相容性預設規則，可編輯及新增 Markdown；一般互審按成員指定，多代理流程按審查位置指定。
- **意見模式**：同時向 2 至 4 位 Claude、GPT 或已啟用的本地成員蒐集獨立唯讀意見，另用一輪整理共識、分歧及計畫。有效回覆不足兩份時保留結果，不捏造共識；採用提案只會建立草稿。
- **worktree 隔離**：每項對話任務建立自己的分支及工作區；同一任務的順序代理在該區交接，不是每位代理各開一個工作區。兩側乾淨且已提交時，用 Git 預演合併；版本改變或衝突會拒絕套用。合併須明確確認，分支與 worktree 均保留。

實作入口、資料保存與限制見 [協作控制](collaboration.md)，實際測試與建置見 [驗證紀錄](visual-identity-validation.md)。
