# CCA 的開發目的

CCA 要處理的是多階段開發中的交接、審查與驗收。模型回覆可以流暢，但這不代表進度完整、修改正確或測試真的執行過。使用者需要一個能把需求、實際操作與交付結果連起來的工作區。

## 起點與問題

作者使用 OpenAI 為 Claude Code 開發的 Codex 插件時，發現既有雙模型協作方式仍不符合期待，於是建立獨立的 Windows 桌面與 CLI。這個起點延伸成四項具體目標：

1. 長任務或模型接手時，保留原始要求、後續修正、實際變更、執行狀態與未完成工作，降低人工重述的負擔。
2. 讓撰寫與審查分開，審查意見可以回到檔案與執行紀錄核對，降低只憑模型語氣或雙方同意就接受成果的情況。
3. 讓計畫、工具權限、修改範圍與回滾入口清楚可見，使用者能介入、調整或停止工作。
4. 保留本機工作方式與既有 CLI 登入，模型、供應商與表達風格可以替換，技術要求保持一致。

## 現在如何實現

| 目標 | 已有機制 | 能力界線 |
| --- | --- | --- |
| 持續交接 | 任務紀錄、實際 Git 差異、額度接手、計畫版本與待辦 | 交接有長度上限；接手模型仍須重讀必要檔案 |
| 可核對的審查 | 交叉審查、唯讀意見、取證檢查、主機測試證據與相同案例重現 | 測試只涵蓋執行的情境；模型共識不是正確性證明 |
| 可掌握的操作 | 計畫核准、權限選擇、變更檢視、worktree、檢查點與回滾 | 一般測試不是權限沙箱；外部副作用不能靠檔案回滾撤銷 |
| 可替換的參與者 | Claude Code、Codex、API 與唯讀本地模型；本機性格資料 | 各後端能力與用量回報不同；性格不能提高權限或降低規範 |

## 如何判斷是否有進步

改進應能用實際工作案例核對：接手後遺漏的要求是否減少、審查問題能否重現、過期驗證是否被標示、保存失敗是否能恢復、使用者能否辨認下一個需要處理的動作。這些是評估方向，並非已達成的效能數據。

## 開源與個人設定

新安裝不啟用性格，公開原始碼與 EXE 不包含特定角色的背景、提示詞或預設指派。自訂性格保存在資料目錄；可選的預設由同目錄的 `persona-presets.json` 載入。更換語氣不改變工作規範、工具權限與驗收依據。

本機對話與設定不隨專案公開。CLI 登入及 API 呼叫仍可能依使用的後端將資料送往服務提供者，不能將「本機保存」解釋為所有資料都不離開裝置。
