# 工作台與軟體更新

## 上下文來源

對話標題旁的列表按鈕開啟「工作台」，包含上下文來源與待送指令。CLI 對應 `/context`、`/queue`。

來源紀錄由主機在送出文字前建立，保存原始需求、CCA 組合的交付文字、角色與規則指示、模型、權限、工作區、送出前檢查點與交接索引筆數。這涵蓋一般對話、主要協作流程、唯讀本地審查及獨立意見模式。

「已提交」只表示主機曾嘗試交付；執行與完成狀態依後端事件更新。外部 Claude／Codex 的內部歷史、實際截斷、注意力與未回報資料，均不能由 CCA 保證。工具活動只代表後端曾回報該路徑，未取得內容及版本時顯示未知；不能當成主機驗收證據。

每個對話保留最近 20 輪，每份文字最多保存 64 KiB，截短時同時保存原始 byte 數。舊版本回覆不補造來源。紀錄保存在資料目錄的 `desk/<conversation-id>.json`，可能包含對話中的私人文字，應與聊天紀錄一樣保管。

## 待送指令

回覆期間按 Enter 會加入佇列，主機原子保存成功後才清空輸入欄。可編輯、上移、下移或取消尚未送出的項目；CLI 為：

```text
/queue
/queue add 指令內容
/queue edit ID 新內容
/queue move ID 1
/queue remove ID
/queue pause
/queue resume
/queue retry ID
```

順位從 1 起算。每個對話最多 32 筆，每筆最多 64 KiB；加入新項目時清掉已完成項目。

這是「整個任務完成後再送出」的佇列，不會在任意工具呼叫中途注入文字。工作忙碌、審查暫停、要求核准、工作區準備中時不會交付。工作失敗、停止或 CCA 重啟後，需要明確重新啟用；送出意圖會先保存，中斷項目需先確認重試，因此重啟不會默默執行第二次。草稿計畫須先處理，不能由佇列自動核准。

清除對話會先清除其佇列及來源紀錄；保存失敗則保留對話。損壞的佇列檔不會被空檔覆蓋，須先備份與修復。

## 版面與閱讀

「使用者設定 → 版面與閱讀」提供閱讀、協作、審查三種欄寬與文字密度預設，以及 13–19 px 的對話字級。頻道欄可調為 180–380 px，資訊欄為 260–520 px。拖曳邊界，或聚焦分隔線後用方向鍵、Home、End 調整。窄視窗保留至少 400 px 的主要閱讀空間，資訊欄沿用抽屜。

設定由主機保存；失敗時復原原設定，不清除訊息或輸入草稿。CLI 的閱讀區由終端機欄列與字型控制，不套用桌面的像素欄寬。

## 更新來源與版本

1.0.1-oss 起有兩個更新來源，設定 → 軟體更新（CLI：`/update`）分開顯示：

- **遠端發行站：未啟用。** 先前保存的 HTTPS `manifest.json` 位址只顯示、不可編輯，CCA 不連線檢查。`update.source` 一律回覆「遠端更新尚未啟用」。
- **本機資料夾：已啟用、自動建立。** 位置是資料目錄的 `installers`（一般為 `%APPDATA%\CCA\installers`；測試時跟著 `CCA_DATA_DIR`），第一次掃描時建立。可放入 `make_release.py` 產生的發行資料夾、直接放清單與執行檔，或單一個 `ChatClaudeAgent*.exe`。

CCA 每 5 秒比對資料夾的檔名、大小與修改時間，有變動才完整檢查。只接受產品名稱為 ChatClaudeAgent、外殼類型與目前程式相同（桌面版只看 `ChatClaudeAgent.exe`，CLI 只看 `ChatClaudeAgent-CLI.exe`）、版本比目前新且內容與本機不同的檔案；連結、目錄連接點與指向資料夾外的清單項目都略過。單一執行檔沒有清單，就以掃描時讀到的內容計算 SHA-256，安裝前再核對一次，期間被換掉就取消。同版本同時有清單與單一執行檔時，優先使用清單。

「發現新安裝包時自動更新」預設開啟：所有任務、驗證與待送佇列都停止後，顯示提示並在 10 秒後關閉、替換、重新開啟；這 10 秒內開始新工作會延後，也可按「取消這次自動更新」（CLI：`/update cancel`）。有工作執行時狀態為「等待目前的工作結束後自動更新」。安裝失敗不自動重試同一版本，直到資料夾內容改變。關閉自動更新後，仍可按「更新並重新開啟」手動安裝。CLI 只在 `/update` 之後或有可安裝版本、排程、錯誤時顯示更新狀態，例行掃描不洗版。

版本規則：

```text
1.0.0- → 1.0.0-oss → 1.0.0-luna → 1.0.0-terra → 1.0.0-sol → 1.0.1- → 1.0.1-oss
1.0.0-astra → 1.0.1-
```

`src/version.hpp` 的數字版本第四欄是後綴序號（無後綴 0、oss 1、luna 2、terra 3、sol 4、astra 5），例如 1.0.1-oss 是 `1, 0, 1, 1`。

修訂版本後綴（`oss → luna → terra → sol → astra`）統稱「重大規範化」：發表、發行說明與更新視窗都用這個名稱，不再稱「註釋」。每個後綴版本都有自己的產品發表，製作方式見 宣傳片與產品發表。

1.0.1-astra 起另有特殊版本（Haiku、Sonnet、Opus、Fable），各自從 0.0.1 起算，只在使用者選擇時切換，見 [版本路線](editions.md)。`astra` 是同一數字版本中排序最高的重大規範化，高於 `sol`，可在一般更新序列中直接發布。舊的 `1.0.0` 與 `1.0.0-` 等價。相同版本不重裝、較舊版本不降版；即使版本較新，檔案 SHA-256 相同也不顯示可安裝更新。後綴只接受上述小寫名稱。

可用 `python tools/make_release.py --next 1.0.0-sol` 查詢下一版；加 `--major-update` 產生同版 `astra`。這只輸出版本，不修改或發布檔案。

## 建立發行包

先修改 `src/version.hpp` 並建置兩個外殼，再執行：

```powershell
python tools/make_release.py --desktop build/ChatClaudeAgent.exe --cli build/ChatClaudeAgent-CLI.exe --output build/release-1.0.0 --notes "發行說明"
```

新目錄包含兩個 EXE 與 schema 1 的發行清單。清單各 `files.desktop`／`files.cli` 項目包含相鄰檔名 `name`、byte 數 `size` 與小寫 `sha256`。把整個目錄複製到本機更新資料夾即可更新。遠端程式碼仍只支援與清單同目錄的檔案、不跟隨 HTTP 重新導向，但遠端來源目前未啟用。這個流程不會自行推送或部署。

HTTPS 驗證傳輸與來源，SHA-256 核對下載內容；兩者不等於獨立的發行者數位簽章。發行來源具有提供程式碼的權限，因此必須是受信任的位置。

## 安裝與復原

桌面及 CLI 分別更新正在執行的單一 EXE，所有 UI 與工作程序資源已內嵌，不改動另一個外殼、專案、性格檔或聊天資料。

1. 確認沒有執行中任務、準備工作、驗證或已啟用佇列。
2. 在背景讀取安裝包，核對大小、SHA-256、x64 PE、產品名稱、版本與外殼類型。核對期間仍顯示 CCA，不先關閉。
3. 明確保存設定、對話、用量與佇列；任何保存失敗均取消關閉。
4. 複製目前 EXE 作為獨立更新程式，收到準備確認後才關閉主程式。
5. 更新視窗用既有的雙 C 圖標表示進度：等待時兩個筆畫輕輕呼吸，核對時靠近，替換時鎖在一起並閃一下訊號色外框，啟動時外框緩緩明滅，完成時變成訊號色並畫出打勾；失敗時變紅、分開。下方的步驟條（等待關閉、核對、替換、啟動、完成）標出目前在哪一步，進度條依階段推進，不顯示百分比數字。系統關閉動畫（或設定關閉動態）時，所有轉場立即完成。
6. 等待原程序退出，以同磁碟替換保留 `.cca-previous-<雜湊前綴>` 復原檔；重新啟動，等候最多 30 秒的就緒確認。失敗則嘗試恢復並開啟舊版。

更新程式是唯一需離開 CCA 子程序 Job 的程序；宿主 Job 不允許分離時，更新會取消，CCA 保持開啟。不使用系統管理員提權或關閉安全軟體。更新暫存、`result.json` 與 `update.log` 留在本機資料目錄的 `updates` 子目錄，供檢查；舊 EXE 復原檔亦保留，不自動刪除。

### 自動除錯

更新程式在 CCA 關閉之後才動手，所以能先查的先查，查不出來的寫清楚：

- **關閉前的預檢**：CCA 所在的資料夾要能寫入、磁碟要有足夠空間（約新版大小的三倍再加 16 MB）；不行就直接在 CCA 還開著時說明原因，不進入替換。
- **清掉上次留下的殘檔**：`.cca-next` 若已核對符合新版就沿用，否則刪除；內容與目前 EXE 相同的舊備份刪除，內容不明的備份只移成 `.stale`，不刪除。
- **暫時被占用會自己重試**：防毒軟體或檔案總管短暫占住檔案（權限不足、共用違規、檔案被載入）時，最多重試 6 次、每次多等一下，視窗上寫第幾次重試；其他錯誤（磁碟已滿、路徑不存在、唯讀等）不重試，直接停下。
- **新版啟動失敗要說原因**：新版立刻結束時記下結束碼（例如缺少系統元件、當機）；30 秒內沒有回報就說沒有回報。之後一律復原舊版。
- **診斷寫進兩個檔**：`result.json` 的 `diagnosis` 是給人看的幾句話，`update.log` 是逐步的時間紀錄；失敗時視窗與對話框也列出同樣的原因。
- **舊的暫存會清**：`updates` 底下超過兩週沒動的資料夾，只刪更新程式自己寫的檔案（`payload.exe`、`broker.exe`、`plan.json`、`result.json`、`update.log`）。

每一步仍以雜湊核對；任何一步不確定，就保留舊版。

## 驗證

```powershell
.\build.bat desk-test
python tests/test_update_broker.py   # 含殘檔清除、暫時鎖定重試、持續鎖定的診斷（請用 PowerShell 執行：Bash 的作業物件不允許更新程式脫離）
node tests/desk_browser.cjs
```

原生測試使用 `CCA_DATA_DIR` 隔離資料，涵蓋資料夾自動建立、空資料夾、非 CCA 檔案略過、指紋變動與清單不能指向資料夾外；更新整合測試只替換暫存目錄中的測試 EXE，包含清單與「資料夾內單一執行檔」兩種安裝、真正的啟動確認與啟動失敗回復，不關閉日常使用中的 CCA。瀏覽器測試使用模擬主機與 Edge，檢查遠端顯示未啟用、資料夾路徑、自動更新開關與取消排程，不消耗模型額度。
